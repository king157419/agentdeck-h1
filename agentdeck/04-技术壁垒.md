## 一、一句话结论（v2 修订）

**硬件不是护城河，6 个月就能被抄。我们能守住的是三样"越做越厚"的东西：跟着各家 agent 每月变化持续维护的适配层、跨厂商的高危操作物理确权（Hardware 2FA for Agents）与团队策略、国产 agent 厂商的合作关系。** "审批数据越用越准"的数据飞轮不算护城河（见壁垒 2）。它们今天都还薄，所以本文最后给出按季度的建设路线图。

| 候选壁垒 | 今天的强度 | 12 个月后可能的强度 | 说明 |
|---|---|---|---|
| 硬件设计 | 无 | 无 | 公开物料、DIY 只要约 $30 |
| 多 agent 适配层 | 弱～中 | 中～强 | 取决于覆盖家数和修复速度 |
| 高危操作物理确权 + 跨厂商策略（v2 修订） | 弱 | 中 | 价值在"跨厂商统一 + 团队审计 + 身份绑定"，不在数据量；数据飞轮打不过官方分类器 |
| 模板 / 团队策略锁定 | 无 | 弱～中 | 取决于团队版是否起量 |
| 国产 agent 合作 | 无 | 中 | 有先发窗口，需 2027 上半年拿下 |
| 供应链成本 | 弱 | 弱 | 只对海外品牌成立 |

## 二、什么不是护城河（v2 修订）

### 硬件

**结论：任何一个会画 PCB 的团队都能在一个季度内做出同等硬件。**

- Codex Micro 被大量评论指出就是 Work Louder 现成的 Creator Micro 2 换皮 [1][2]。
- Anthropic 官方公开了蓝牙硬件协议，社区已出现至少 5 个移植版本，用的都是约 $20～30 的 ESP32 开发板 [3][4]。
- 带屏控制器是成熟品类：Stream Deck、Logitech MX Keypad、Ulanzi D200 都已量产 [5][6][7]。（v2 修订）罗技 MX Keypad 2026-09 发布，只卖 $99.99，官方原生支持 GitHub Copilot、Claude Code、Codex [35]；优篮子 D200 上已经有免费的同名 AgentDeck 插件 [28]。
- 国内个人开发者已经用"国产带屏键盘改刷固件 + ESP32"做出 Claude Code 专用键盘 [8]。

**所以：** 硬件只决定"体验好不好"，不决定"别人能不能做"。我们不在硬件上申请护城河叙事。

### 供应链成本

**结论：深圳供应链只对海外品牌是优势，对国内对手不是。**

国内最近的对手 Ulanzi 就是深圳公司（深圳唯迹科技）[9]。整机物料成本目前只有我方粗估，没有工厂报价，**不作为对外论据** [10]。

## 三、什么是护城河（以及它现在有多厚）（v2 修订）

### 壁垒 1：多 agent 适配层——跟着各家每月的变化走

**结论：每家 agent 的"钩子"（agent 在关键时刻通知外部程序的接口）能力不同、而且一直在变；能长期把 8～10 家都维护好，本身就是工程壁垒。**

**各家能力差别很大：**

| agent | 能否由外部直接回答"批准/拒绝" | 来源 |
|---|---|---|
| Claude Code | 能（`PermissionRequest` 钩子返回 allow/deny；超时自动退回终端提示） | [11] |
| Codex CLI | 能（同类钩子；但部分字段写明"目前一律拒绝"，不能用） | [12] |
| Cursor | 部分：只能做"事前拦截"，不能替用户回答弹窗 | [13] |
| Gemini CLI（已并入 Antigravity） | 部分：只能拒绝，未查到"询问"选项 | [14][15] |
| 腾讯 CodeBuddy | 有 27 个钩子事件，含权限请求；能否代答【待实测】 | [16] |
| 阿里 Qwen Code | 有 23 个钩子事件，含权限请求，支持本地 HTTP 接收；能否代答【待实测】 | [17] |
| 月之暗面 Kimi Code | 有 20 个事件，权限请求**只能通知、不能阻断** | [18] |
| 字节 Trae | IDE 有钩子并可导入 Claude Code 钩子；是否有权限请求事件【待实测】 | [19] |

**而且一直在变（过去 6 个月的例子）：**
- Google 把 Gemini CLI 并入 Antigravity CLI，个人服务 2026-06-18 终止 [15]。
- Codex 的钩子文档整体搬了域名 [12]；审批策略里的 `untrusted` 选项已被取消 [20]。
- Claude Code 从 2026-08-14 起默认开启 auto mode，审批次数大幅下降 [21]。
- Claude Code 的 `idle_prompt` 通知会在刚回复完时误报"在等你" [22]。
- Trae 的 SOLO 在 2026-06 升级为 TRAE Work [23]；Windsurf 改名 Devin Desktop [24]。

**为什么难抄：** 单家适配一个周末就能做（agentsd 就是例子 [25]），但同时维护 8～10 家、在每家更新后 48 小时内修好、在 Windows / macOS / Linux 三个系统都可靠，需要持续的人力和自动化测试。大厂不会做（支持竞争对手），小团队做不久（开源编排器的弃用速度说明了这点 [26]）。

**为什么还不算厚（v2 修订）：** VibeKeys 已覆盖 6 家海外 agent，而且它的开源组件已经接了 Claude Code 钩子推状态 [27]；开源项目 puritysb/AgentDeck 覆盖 Claude Code、Codex、Antigravity，已上架 Mac App Store，并作为免费插件上架优篮子插件商店 [28]；罗技 MX Keypad 原生支持 Claude Code 和 Codex [35]。"能显示多家 agent 状态"已经不稀缺。我们的增量在三处：国产 agent、"直接回答审批 + 高危闸门"的深度，以及多家同时在线时不批错窗口的会话定位。

### 壁垒 2：高危操作的物理确权（Hardware 2FA for Agents）+ 跨厂商策略（v2 修订）

**结论：不再讲"数据飞轮"。我们讲的是：日常命令交给 agent 自己的 auto mode，不可逆操作必须在一块独立设备上用手确认——相当于 agent 的硬件双因素认证。它的价值在"跨厂商统一 + 团队审计 + 人和设备绑定"，不在数据量。**

- **为什么不讲数据飞轮**：Anthropic 的对照实验里，人工审查只拦下 13.6% 的危险操作，官方分类器拦下 89% [30]。分类器的数据量和准确率我们都追不上，"我们的审批数据越用越准"在投资人面前站不住。v0.1 里"积累'哪些命令被批准 / 拒绝 / 事后撤销'的数据让分级越来越准"降级为产品内部的规则调优手段，不再作为护城河对外讲。
- **为什么 Hardware 2FA 讲得通**：
  1. auto mode 解决的是"日常命令不用人批"，不解决"不可逆操作要不要人亲手确认"。推主干、改生产、写数据库、改密钥、合并 PR 这一小撮操作，正是团队最想留人工确认和记录的。
  2. 我们的做法：用 `PreToolUse` 钩子做"高危闸门"，即使 auto mode 打算放行，也要在设备上按两次 ✓；闸门只加确认、不替 agent 放行；超时或出错一律拒绝。第一因子是 agent 的判断，第二因子是人手在独立 USB 设备上的物理按键（带屏上显示的随机数校验，焦点在哪个窗口都不影响）。
  3. 和软件弹窗的区别：软件弹窗在被确认的那台电脑、那个窗口里，容易被"随手点掉"；独立设备 + 二次按键 + 只显示原始命令（不显示模型自己写的描述），对提示注入和疲劳更稳。
- **限制 1：** 规则分级（`git push --force`、`curl | sh`、生产主机列表等）谁都能写，单看规则没有壁垒。
- **限制 2：** 命令里可能有密钥和路径，任何统计数据都必须本地优先、用户主动同意才上传。
- **限制 3：** 高危闸门（`PreToolUse`）hub v1.4 已实现，并用真实进程和真实系统热键（F19/F20）验证，但还没在真实 auto mode 的 Claude Code / Codex 会话里测过（见第四节）；`PreToolUse` 和 `PermissionRequest` 叠加时的体验【待实测】。

**可守的部分：** 企业要的是"同一套高危策略管住 Claude、Codex、Cursor、国产 agent，确认动作和具体的人、设备绑定，并留审计"，这是任何单一厂商都不会提供的。对应 Team 版：企业 SSO（飞书 / 企微 / 钉钉 / Okta）、合规仪表盘、私有化部署、MCP 工具白名单（D4）。

### 壁垒 3：模板、工作流与团队策略

**结论：今天为零，只有团队版起量后才成立。**

用户的常用指令模板、按键布局、团队审批策略沉淀在我们的软件里，换设备要重新配置。但个人模板只是几行文字、很容易导出，所以**真正的锁定来自团队策略和审计日志**，不来自个人模板。

### 壁垒 4：国产 agent 生态合作

**结论：最有先发价值的一条，但今天还是零，必须尽快去谈。**

- 国产 CLI 的钩子接口已就位 [16][17][18]，技术上可以接。
- 国内已有"厂商 + 大厂联名"的模板：Ulanzi × 腾讯 WorkBuddy [31]。（v2 修订）但联名不等于独占：优篮子 Vibe Key（AU05）海内外都卖通用版，底层走 Ulanzi Studio 自由映射，官方宣传支持 Claude Code、Codex、千问、豆包 [36]。所以"官方推荐硬件"的价值是渠道和背书，不是排他。
- 国内很多开发者用"Claude Code + 国产模型" [32]，我们做好 Claude Code 适配就能先覆盖他们，再用这批用户数据去谈国产 agent 厂商。
- 目标：成为 2～3 家国产 agent 的"官方推荐硬件"。有先发窗口，但不要指望排他（v2 修订）。

## 四、原型上已经解决的工程难题（真实证据）（v2 修订）

**结论：我们已有可用原型（Windows + 一把现成的 20 键宏键盘 + ESP32 状态屏 + 本机中枢 hub v1），下面的问题都是在真机上踩出来、修好、有测试的（记录见内部开发日志 agentdeck/devlog/devlog.md [37]）。它们证明的是团队执行力和底层经验，而不是专利。**

| # | 问题 | 为什么难 | 我们怎么解决 | 状态 |
|---|---|---|---|---|
| 1 | 宏键盘的按键会"漏"到当前窗口 | Windows 先跑低级键盘钩子、后跑 Raw Input，钩子里分不清按键来自哪块键盘，所以拦不干净 | 用 Zadig 把这把键盘的接口 0 驱动换成 WinUSB，程序直接读 8 字节原始报文，Windows 根本收不到这些按键；其他接口不动 | 已解决，有自动化测试 |
| 2 | Ctrl+Z 被识别成单独的 Z | 这把键盘的出厂宏先单独发一帧 Ctrl，下一帧才发主键 | 在报文解析里加"新鲜修饰键"语义：Ctrl 保持有效直到被下一个主键消耗 | 已解决，录制回放 10/10 |
| 3 | 状态屏在两个会话之间来回闪 | 守护程序（跟随前台窗口）和按键程序（用户选会话）同时往屏幕发焦点 | 用标记文件加 Windows 命名互斥量 `Local\AgentDeckFocus` 做仲裁，同一时刻只有一方能改焦点 | 已解决，有测试 |
| 4 | 批准键可能批错窗口 | 多 agent 并行时，模拟按 Enter 会发给"当前前台窗口"，而前台可能刚被切走 | （v2 修订）**已改为直接回答 `PermissionRequest` 钩子** [11][12]，完全不碰键盘输入：`pc/hub.py` 收到钩子事件后阻塞等待设备按键，再把 allow / deny 写回钩子。旧的"带保护的模拟按键"保留为不支持钩子的 agent 的兜底 | 已实现。用真实 relay / hub 进程（Codex 格式事件）验证：低风险单击返回 `allow`；`git push --force` 第一次只返回 `HOLD! press again`、第二次才 `allow`；拒绝返回 `deny`；hub 不在时 relay 静默退出、agent 走原生提示；极危命令（L3）设备上不能放行（v1.1，`curl … \| sh` 533 ms 退回终端确认，按 ✓ 返回 `locked`）。离线测试：中枢 264 项单元测试（`test_hub*.py`，含演示模式与虚拟 v2 设备窗口）+ 回放自检 12/12，全部通过。**还没在真实 agent 会话里跑过**（见下） |
| 5 | Codex 钩子装上了却一条事件都不来（v2 新增） | Codex 规定新增或改动的钩子要用户在 Codex 里用 `/hooks` 信任后才运行，没信任时静默跳过，不报错 [12] | 加 relay 失败日志定位到"relay 根本没被执行"，查官方文档找到原因；不用跳过信任的参数（信任必须由用户本人做），改为在安装引导里加"/hooks 信任"一步，并检测"看到 Codex 进程 10 分钟仍无 cx 事件"时提醒 | 原因已查清；引导和检测待做 |

另外三条可以写进 BP 的事实：
- 原型已经接入 Claude Code（8 类事件，后台异步，不拖慢会话）和 Codex（8 类事件，含 `PermissionRequest`）的钩子用于状态识别。
- （v2）中枢 hub 已经能直接回答 Claude Code / Codex 的 `PermissionRequest`，高风险命令要按两次，极危命令设备上不能放行，带哈希链审计日志（v1.1）；v1.3 加了 F13–F24 全局热键和置顶 6 槽小浮窗，已用系统按键真机验证（F19 返回 allow、F20 返回 deny）；v1.4 加了 `PreToolUse` 高危闸门（只加不减，两次 ✓ 返回 `{}`，✗ / 超时 deny），同样用真实进程和真实系统热键验证，真实 auto mode 会话待测。任何故障都退回 agent 的原生提示。对外口径："钩子直答已实现，并用真实进程验证；真实 agent 会话的端到端验证进行中"。
- 我们最初把重心放在状态屏上，后来根据调研纠正为"按键控制为核心、屏幕为辅助"——这是本轮战略调整的来源。

**对投资人的诚实说明（v2 修订）：** 第 1 条依赖用户手动换驱动，这在自有硬件上不存在（自有硬件会直接暴露专用通信接口），但说明"拿现成键盘驱动"这条路的门槛不低。第 4 条已从"待实现"变成"已实现、真实进程验证通过"，剩下的缺口是：① 在真实 Claude Code 会话里跑一次（需要本机 `claude` 命令行登录，桌面版凭据不共用）；② 在真实 Codex 会话里跑一次（需要用户先在 Codex 里信任钩子）；③ 用物理键按 ✓（目前测试走的是动作接口，宏键盘的 USB 被另一个程序占着）；④ macOS 版；⑤ 拦 auto mode 自动放行命令的 `PreToolUse` 高危闸门（hub v1.4 已实现并用真实进程验证，真实 auto mode 会话待测）和设备回报的随机数校验（未开发）。极危命令（L3）锁死已在 v1.1 实现并用真实进程验证。这几项都在路演前 6–8 周的验证清单里（D7①）。
